# Problem Diagnosis — วิเคราะห์ปัญหาอย่างเป็นระบบ
# ใช้เมื่อ: เจอ bug, ระบบพัง, หรือมีปัญหาที่ต้องหาสาเหตุ
# หลัก: หา root cause (ต้นตอ) ไม่ใช่แค่แก้ symptom (อาการ)

---

## ทำไมต้องวิเคราะห์ก่อนแก้?

```
❌ วิธีผิด:
เห็น error → เดาว่าพังตรงไหน → แก้มั่ว → แก้ไม่ตรงจุด → เสียเวลา

✅ วิธีถูก:
เห็น error → เก็บข้อมูล → ตั้งสมมติฐาน → ทดสอบ → หา root cause → แก้ตรงจุด
```

---

## Step 1: เก็บข้อมูล (Collect Evidence)

| # | คำถาม | หมายความว่า | ตัวอย่าง Stock | คำตอบ |
|---|---|---|---|---|
| 1 | อะไรที่ "ควรเกิด" (expected)? | ปกติต้องทำงานยังไง | "กดขาย 1 ชิ้น → stock ลด 1" | |
| 2 | อะไรที่ "เกิดจริง" (actual)? | ตอนนี้ทำงานผิดยังไง | "กดขาย 1 ชิ้น → stock ลด 2" | |
| 3 | เริ่มเกิดตั้งแต่เมื่อไร? | timeline ของปัญหา | "ตั้งแต่วันจันทร์ที่ deploy ใหม่" | |
| 4 | เกิดทุกครั้ง หรือบางช่วง? | pattern ของปัญหา | "เกิดเฉพาะตอนขายพร้อมกัน 2 คน" | |
| 5 | เงื่อนไขที่ทำให้เกิดคืออะไร? | trigger (สิ่งกระตุ้น) | "เกิดเมื่อสินค้ามี variant (size/color)" | |
| 6 | มี error message / log ไหม? | evidence จริง | "Error: duplicate key in stock_transactions" | |
| 7 | มีอะไรเปลี่ยนก่อนหน้านี้? | สาเหตุที่อาจเป็นไปได้ | "deploy feature ใหม่เมื่อวาน" | |

### ตัวอย่าง Stock ลด 2 แทน 1:

| # | สมมติฐาน | ถ้าจริง → จะเห็นอะไร | วิธีทดสอบ |
|---|---|---|---|
| 1 | API ถูกเรียก 2 ครั้ง (duplicate request) | log มี request เดียวกัน 2 records | ดู API access log |
| 2 | code คำนวณผิด (logic error) | ทุก transaction ลด 2 ไม่ว่าจะ condition ไหน | ดู source code ส่วนตัดstock |
| 3 | race condition (2 คนทำพร้อมกัน) | เกิดเฉพาะตอนหลายคนขายพร้อมกัน | ทดสอบกด 2 เครื่องพร้อมกัน |

## Step 4: หา Root Cause (ต้นตอ)

```
Root Cause = [สิ่งที่ทำให้เกิดปัญหาจริงๆ]
```

ถาม 5 Why (ถามว่า "ทำไม?" 5 ครั้ง):
```
ทำไม stock ลด 2? → เพราะ API ถูกเรียก 2 ครั้ง
ทำไม API ถูกเรียก 2 ครั้ง? → เพราะ frontend ไม่ได้ disable button หลังกด
ทำไมไม่ disable? → เพราะไม่มี loading state
ทำไมไม่มี? → เพราะไม่ได้ออกแบบไว้
Root Cause: ไม่มี UX pattern ป้องกัน double-click + ไม่มี idempotency ที่ backend
```

---

## Step 5: เสนอวิธีแก้ + Tradeoff

| วิธีแก้ | ข้อดี | ข้อเสีย | เลือก? |
|---|---|---|---|
| A: disable button frontend | เร็ว, ง่าย | ไม่ป้องกัน API call ตรง | |
| B: idempotency key ที่ backend | ป้องกันได้ 100% | ใช้เวลาทำมากกว่า | |
| C: ทำทั้ง A + B | ปลอดภัยที่สุด | ใช้เวลาทำมากที่สุด | |

---

## Step 6: บันทึก

เมื่อแก้เสร็จ → บันทึกลง `07-logs/investigations/`:
- symptom (อาการ) คืออะไร
- root cause (ต้นตอ) คืออะไร
- fix (วิธีแก้) คืออะไร
- lesson (บทเรียน) คืออะไร
- prevention (วิธีป้องกันไม่ให้เกิดอีก) คืออะไร

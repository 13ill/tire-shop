# Tradeoff Discussion — วิเคราะห์ทางเลือก + ข้อดี/ข้อเสีย
# ใช้เมื่อ: ต้องตัดสินใจ approach/technology/pattern — ห้ามเลือกทางเดียวโดยไม่เปรียบเทียบ
# กฎ: ทุกการตัดสินใจต้องมีอย่างน้อย 2 ทางเลือก + tradeoff ชัดเจน

---

## Tradeoff คืออะไร?

**Tradeoff** = สิ่งที่ต้อง "แลก" — ได้อย่างหนึ่ง ต้องเสียอีกอย่าง

```
ตัวอย่าง:
- เร็ว แต่ไม่สวย  vs  สวย แต่ช้า
- ง่ายแต่ไม่ scale  vs  ยากแต่ scale ได้
- ถูกแต่ต้องดูแลเอง  vs  แพงแต่ managed (มีคนดูแลให้)
```

---

## เมื่อไรต้องใช้ Tradeoff Mode?

- เมื่อต้องเลือก technology (เช่น React vs Angular)
- เมื่อต้องเลือก approach (เช่น monolith vs microservice)
- เมื่อต้องเลือกระหว่าง speed vs quality
- เมื่อ owner ต้องการอะไรที่ขัดกัน (เร็ว + ถูก + ดี ← เลือกได้แค่ 2)
- เมื่อมีหลายวิธีแก้ปัญหา

## ตัวอย่าง: เลือก Database สำหรับระบบ Stock

### 1. สิ่งที่ต้องตัดสินใจ
```
คำถาม: ใช้ database อะไรสำหรับระบบ stock?
Context: ระบบ stock ร้านค้า 1 ร้าน, user 5 คน, สินค้า ~500 SKU
Constraints: budget ต่ำ, ต้อง deploy เร็ว, ดูแลคนเดียว
```

### 2. ทางเลือก

| ทางเลือก | คำอธิบาย |
|---|---|
| A: PostgreSQL (self-hosted) | ติดตั้งเอง, ฟรี, powerful |
| B: Supabase (managed PostgreSQL) | hosted ให้, มี API สำเร็จรูป, free tier |
| C: Firebase Firestore | NoSQL, real-time, ง่ายมาก |

### 3. เปรียบเทียบ

| มิติ | A: PostgreSQL | B: Supabase | C: Firebase |
|---|---|---|---|
| ⏱️ เวลาทำ | นาน (setup เอง) | กลาง | เร็วมาก |
| 💰 ค่าใช้จ่าย | ฟรี (แต่ต้อง server) | ฟรี (free tier) | ฟรี (free tier) |
| 🔧 Maintain | ยาก (ดูแลเอง) | ง่าย (managed) | ง่ายมาก |
| 📈 Scale | ดีมาก | ดี | ดีแต่แพง |
| ⚠️ Risk | ต่ำ (control เต็ม) | กลาง (vendor lock) | สูง (vendor lock + แพง) |
| ↩️ ย้อนกลับ | ย้ายได้ง่าย | ย้ายได้ (PostgreSQL) | ย้ายยากมาก |

### 5. คำแนะนำ
```
แนะนำ: B (Supabase)
เหตุผล: ได้ PostgreSQL + ง่าย + ฟรี + ย้ายออกได้ถ้าต้องการ
ข้อควรระวัง: ถ้า user เยอะมากต้อง upgrade plan
ถ้าต้องเปลี่ยนใจ: ย้ายไป self-hosted PostgreSQL ได้เพราะ schema เหมือนกัน
```

# Risk Analysis — ประเมินความเสี่ยง
# ใช้เมื่อ: เข้าใจระบบแล้ว → ต้องรู้ว่า "ถ้าพังจะเกิดอะไร" ก่อนลงมือทำ
# หลัก: ทุกการเปลี่ยนแปลงมีความเสี่ยง — ต้องรู้ + เตรียมรับมือ

---

## ทำไมต้องประเมิน Risk?

```
ไม่ประเมิน risk = เหมือนข้ามถนนโดยไม่ดูซ้ายขวา
อาจรอดได้ 10 ครั้ง แต่ครั้งที่ 11 โดนชน
```

## 5 มิติของ Risk ที่ต้องประเมิน

### 1. Performance Risk — ระบบจะช้าลงไหม?

| คำถาม | หมายความว่า | ตัวอย่าง Stock | คำตอบ |
|---|---|---|---|
| เพิ่ม query ใหม่ไหม? | database ทำงานหนักขึ้น | "เพิ่ม JOIN 3 table ต่อ 1 request" | |
| มี loop ที่อาจโตไหม? | ข้อมูลเยอะ = ช้า | "loop สินค้า 10,000 รายการ" | |
| cache ยังใช้ได้ไหม? | อาจต้อง invalidate (ล้าง cache) | "เปลี่ยน stock → cache เก่า = ข้อมูลผิด" | |
| concurrent users รับไหวไหม? | หลายคนใช้พร้อมกัน | "5 คนตัด stock เดียวกันพร้อมกัน" | |

### 2. Data Risk — ข้อมูลอาจเสียหายไหม?

| คำถาม | หมายความว่า | ตัวอย่าง Stock | คำตอบ |
|---|---|---|---|
| migration (ย้ายข้อมูล) ต้องทำไหม? | อาจทำข้อมูลหาย/ผิด | "เปลี่ยน schema → ข้อมูลเก่าต้อง convert" | |
| data corruption เป็นไปได้ไหม? | ข้อมูลเสียหาย | "stock ติดลบ เพราะ race condition" | |
| backup มีไหม? restore ได้ไหม? | ถ้าพังกู้คืนได้ | "backup ทุก 6 ชั่วโมง, restore ใน 30 นาที" | |
| data ที่หายไป recover ได้ไหม? | ถ้าลบผิดทำยังไง | "มี soft delete + audit log" | |

### 3. Security Risk — มีช่องโหว่ไหม?

| คำถาม | หมายความว่า | ตัวอย่าง Stock | คำตอบ |
|---|---|---|---|
| authentication (ยืนยันตัวตน) ครบไหม? | มีคนเข้าถึงที่ไม่ควรไหม | "API ไม่มี auth → ใครก็แก้ stock ได้" | |
| authorization (สิทธิ์) ถูกไหม? | แต่ละ role ทำได้แค่ที่ควร | "พนักงานทั่วไปไม่ควรลบ stock ได้" | |
| input validation มีไหม? | ป้องกัน data ผิดรูปแบบ | "ใส่ stock จำนวน -999 ได้ → stock ลบ" | |
| sensitive data เก็บถูกไหม? | ข้อมูลสำคัญต้องเข้ารหัส | "password, API key ต้อง encrypt" | |

### 4. Deployment Risk — deploy แล้วพังไหม?

| คำถาม | หมายความว่า | ตัวอย่าง Stock | คำตอบ |
|---|---|---|---|
| rollback (ย้อนกลับ) ทำได้ไหม? | ถ้า deploy แล้วพัง กลับได้ไหม | "revert deploy ได้ใน 5 นาที" | |
| breaking change มีไหม? | ของเก่าจะพังไหม | "เปลี่ยน API response → frontend เก่าพัง" | |
| ต้อง downtime ไหม? | ต้องปิดระบบระหว่าง deploy | "migration ต้องปิด 10 นาที" | |
| deploy ตอนไหนปลอดภัย? | หลีกเลี่ยง peak hour | "deploy ตอนตี 2 ไม่ใช่ตอนเที่ยง" | |

### 5. Business Risk — ธุรกิจได้รับผลกระทบไหม?

| คำถาม | หมายความว่า | ตัวอย่าง Stock | คำตอบ |
|---|---|---|---|
| ถ้าพัง ใครเดือดร้อน? | impact ต่อคน/ธุรกิจ | "ร้านขายของไม่ได้ = เสียรายได้" | |
| เสียเงินเท่าไรถ้าพัง 1 ชั่วโมง? | คิดเป็นตัวเลข | "เสีย ~5,000 บาท/ชั่วโมง" | |
| มี SLA (ข้อตกลงระดับบริการ) ไหม? | สัญญาว่าต้อง uptime เท่าไร | "ต้อง uptime 99.9%" | |
| กฎหมาย/compliance กระทบไหม? | ผิดกฎหมายหรือระเบียบไหม | "ต้องเก็บ log ตาม พ.ร.บ. คอมพิวเตอร์" | |

### ระดับ Risk:
- 🔴 **Critical** — ต้องแก้ก่อนทำ / ต้องมี mitigation plan
- 🟡 **Medium** — ยอมรับได้ แต่ต้อง monitor
- 🟢 **Low** — ยอมรับได้ ไม่ต้องทำอะไรพิเศษ
